# 微信发送开销与业务空闲判定

诊断阶段使用只读进程扫描与合成数据测量；文末单独记录更新服务后的授权真实发送验证。下列基线与合成耗时不是端到端发送耗时，也不代表网络送达速度。

## 旧扫描基线

通过 Node `performance.now()` 包围顺序执行的三个样本；PowerShell 使用系统绝对路径、`-NoLogo -NoProfile -NonInteractive`。完整扫描调用改造前的 `scanWindowsProcesses()`，仅记录耗时和实例数量；账号与进程快照只在内存中存在。

| 操作 | 第一次 | 第二次 | 第三次 |
| --- | ---: | ---: | ---: |
| PowerShell 空启动 | 281.02 ms | 247.84 ms | 264.34 ms |
| 完整只读扫描 | 1346.61 ms | 1242.96 ms | 1434.64 ms |
| Node 归一化 | 1.44 ms | 0.22 ms | 0.28 ms |

三个完整扫描均返回一个实例。旧发送路径在准备前和原生提交前各执行一次 `active()`，每次触发完整新扫描。按本轮扫描中位数估算，两次扫描约 2693 ms；这只是串行扫描预算，不包含媒体准备、原生队列、回调和网络。

`CurrentAccount.cs` 的 SHA-256 缓存原本已经存在，但每次启动独立 PowerShell 都会重新创建该缓存。列表扫描的短缓存不能直接替代发送前 PID、精确创建时间与账号身份的新鲜核对。

## 本地合成开销

测量使用独立 `.local/wechat/performance/<随机目录>/`。日志和发送账本均为新建合成文件；没有读取真实账本、联系人或聊天数据。每次账本事务仍保留跨宿主锁和原有落盘顺序，未为加速跳过幂等预留。

| 操作 | 样本 | 本轮结果 |
| --- | ---: | --- |
| JSONL 单条日志 | 10 | 中位 1.595 ms，范围 0.997–4.546 ms |
| 新请求账本预留 | 10 | 3.461–7.287 ms |
| 账本结果更新 | 10 | 3.485–6.746 ms |
| 512×512 合成 PNG，上传校验与暂存 | 3 | 中位 30.257 ms |
| 同一 PNG，worker 读取与再次校验 | 3 | 中位 29.862 ms |
| 2048×2048 合成 PNG，上传校验与暂存 | 3 | 中位 168.085 ms |
| 同一 PNG，worker 读取与再次校验 | 3 | 中位 143.405 ms |

PNG 为程序生成的纯色像素。编码大小分别为 6275 与 88107 字节；像素解码开销比编码体积更有解释力。测试不覆盖复杂动画、大型账本、杀毒扫描、锁争用、原生缓存写入或网络上传；不能从这些少量样本推断 p95。

## 本阶段优化

- 原生队列对象和文本回调继续使用原有 1000 ms 延迟释放；独立 worker 继续保留到所属微信退出。没有缩短所有权保留时间，也没有将空闲计数用作卸载依据。
- 每个版本独立实现业务计数。队列任务只有 `completed === true` 才退出业务忙状态；错误、取消且未完成的任务仍阻止提交。文本回调只有原生已执行 destroy，且请求已有 `accepted` 或 `failed` 结果，才退出业务忙状态。未回执或 `unknown` 仍阻止发送。
- `inspect()` 同时提供活跃计数与保留对象数量。宿主空闲等待仅依据 `pendingTasks`、`pendingCallbacks`、`activeReads`；保留内存本身不再额外拖慢下一项操作。
- 图片操作保留资源准备前的账号核对、一次空闲等待、资源账号/联系人/摘要核对、写入后提交前的再次账号核对，以及原生 prepare/send 各自的业务忙守卫。移除了图片流程中重复的第二轮宿主空闲轮询。

上传与 worker 中的两次完整图片解码暂时保留。要消除其中一次，需另行实现能够跨进程核对内容摘要与不可变字节的媒体验证凭据，不能直接相信调用方提供的“已校验”标记。

## 验证

`node --test platforms/wechat/runtime/tests/business-idle.test.mjs platforms/wechat/runtime/tests/image-send-operation.test.mjs platforms/wechat/runtime/tests/version-contract.test.mjs`：11 项通过。测试覆盖两个版本的完成/销毁/未知状态、保留对象不被提前删除、活跃操作阻断、轮询失败、图片单次空闲等待、资源归属异常与不重试。

根代理实现发送前一次最终新鲜扫描与持久只读扫描器后，同轮只读样本为：冷启动 1744.19 ms，随后热调用 293.89、250.21、252.12 ms。热调用中位数 252.12 ms；本轮相对于旧的两次扫描预算 2693 ms 降低约 91%，只适用于扫描开销比较。冷启动仍需初始化，不能描述为所有发送均有相同比例提升。

## 授权现场验证

仅刷新经端口、绝对可执行路径和命令行确认的本项目开发宿主；5 个已存在的原生所有权 worker 保留，没有停止微信或卸载脚本。恢复原工作身份后，读取联系人并核对仍只有已授权的唯一测试联系人，账号及目标不匹配则不发送。

| 操作 | 本轮单次耗时 | 结果 |
| --- | ---: | --- |
| 新原生运行初始化、读取并绑定联系人 | 4704 ms | active，唯一目标已绑定 |
| 新文字请求 | 798 ms | HTTP 200，submitted |
| 新 240×160 合成 PNG 请求 | 1318 ms | HTTP 200，submitted |

提交耗时由请求前到收到原生回执计时，不包含界面操作；`deliveryConfirmed` 均为 false，没有将原生提交描述为已证明网络送达。没有未知结果重试或批量发送。现场样本各一次，不能据此承诺固定延迟或网络速度。所有真实账号、联系人、请求编号、媒体与运行快照均留在被忽略的本地目录，不进入提交。

完整 `npm test` 108 项、`npm run check` 与 `git diff --check` 通过；新增扫描传输回归覆盖固定指令、连续新鲜快照、旧 scanner 复用、损坏响应拒绝、取消与超时、排队取消不进入输入管道。发送回归验证每次新提交只执行一次最终新鲜扫描，PID 复用仍在原生提交前被拒绝；前置核对失败记为确定未发送，不误写成原生结果未知。
